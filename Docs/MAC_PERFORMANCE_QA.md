# macOS responsiveness performance acceptance — 2026-09-27

Scope: `codex/mac-performance-polish`, based on `e4d6b84` (`origin/main`). Version remains **1.0.4 (9)**. Native appearance, monitor cadence, SwiftData V5, configuration/credential formats and connection protocols are unchanged. iOS is compatibility-only.

## Implementation and invariants

- Startup fetches connection routes, advanced settings and unfinished gaps in batches. Historical curves hydrate in bounded batches, prioritizing selected/visible hosts. Fresh snapshots merge by timestamp; a failed read is retried independently so it cannot starve other hosts.
- macOS owns one history service with its own `ModelContext`. All SwiftData operations remain on `MainActor`. Automatic/manual maintenance share a task, yield between committed work units and use the existing shutdown deadline; exit does not start maintenance.
- Retention operates on complete minute/fifteen-minute buckets. Each server/bucket retires only after its aggregate is durable. Partial work remains retryable after cancellation or failed fetch/encoding/save. A pathological single-server bucket above 4,096 source records reports an error without partial retirement instead of monopolizing the main actor; ordinary monitoring produces far fewer records per minute. Initial storage accounting uses bounded UUID keyset pages and reconciles committed changes during the scan. It does not restart under sustained writes.
- Dashboard caches directory/search/sort projections and includes usernames in search. Metadata/configuration changes invalidate the cache; monitoring values, scrolling and geometry do not rebuild directory indices.
- SFTP keeps the 30 pt native row height. Scroll anchors are controller-owned, non-published state. Visible IDs, ID lookup and selection are updated only with relevant data/filter changes. Hidden targets are deselected; same-directory refresh and view remount preserve surviving selection/anchor.
- Editor search builds a cancellable revision/query index off the main actor; caret feedback uses binary search. The 10,000 count cap does not cap navigation. Directional fallback preserves wrap, case-insensitive and UTF-16 semantics. IME, undo and draft persistence retain their existing ownership.
- Terminal highlighting compiles the search expression per query and uses a 256-entry incremental cache keyed by exact text, cell widths and rule/search version. A cache hit avoids constructing the UTF-16-to-column map. Output receipt, command ordering and recording are unchanged.
- Performance markers have fixed names only: `app.bootstrap`, `dashboard.filter`, `history.maintenance`, `history.batch`, `sftp.projection`, `sftp.table_update`, `editor.search`. They never contain hostnames, paths, commands or file content.

## Reproduction and measurement boundaries

Run `Scripts/benchmark-macos.sh` from any directory. It uses Release `-O`, complete concurrency checks, isolated in-memory fixtures, three warmups and thirty interaction samples (ten startup-query samples). `SERVERDASH_DERIVED_DATA` can reuse build products; `SERVERDASH_BENCHMARK_OUTPUT` chooses the result parent. Each run gets a unique directory with toolchain metadata, logs, xcresult, resource totals and fresh benchmark JSON. It never deletes existing build/result directories.

The baseline algorithms are replayed alongside the current implementation in the **same optimized test binary**. This controls toolchain/fixture differences, but is not a historical application's complete launch time. Startup query substeps and complete synchronous `bootstrap` are reported separately. Historical summary, maintenance, editor index construction, cursor lookup, terminal hot-row calculation and file projection have distinct scopes.

Native QA runs use `.macqa`, an in-memory database, synthetic services and disabled network. Available routes include 100/1,000 hosts, 10,000 SFTP entries, 1.3M/8 MiB editor text and 1/4/16 terminal panels. `--fixture-editor-size 1300000|8mib` selects large editor text. CUA/AX wall-clock timings include automation and accessibility traversal; they are not event-to-frame or main-thread timings. `sample` observations and physical footprint are reported separately. `/usr/bin/time` test resource totals are not the QA application's retained memory. The JSON `testHostResourceUsage` fields use `getrusage(RUSAGE_SELF)` and describe the cumulative XCTest host peak, not the peak of an individual operation or the native QA app.

## Native SFTP window measurement and sampling evidence

The isolated Release QA app displayed 10,000 files in a **1440×900 light** window. Both runs used three warmups and thirty measured search/clear pairs. [ui-baseline.json](Performance/2026-09-27/ui-baseline.json) and [ui-optimized.json](Performance/2026-09-27/ui-optimized.json) preserve every supplied raw sample and source hash, and provide a common `samples` array and scope: the baseline source has 33 samples, so its first three are excluded from the summary; the optimized source already has only the 30 measured samples. P95 uses the nearest-rank method. These files are separate from the six unchanged computation reports above.

- Search CUA/AX wall-clock median **1,066.5 → 1,382.5 ms** (**29.6% slower**), P95 **1,479 → 1,489 ms** (**0.7% slower**).
- Clear-search CUA/AX wall-clock median **1,997 → 5,838 ms** (**192.3% slower**), P95 **6,034 → 6,262 ms** (**3.8% slower**).

**The native interaction measurement does not show a speedup.** Both ordered runs shift from lower-latency early samples to approximately six-second clear/AX snapshots later; the later phase occupies a larger share of the optimized run and raises its median. The values include CUA pacing and complete accessibility-tree traversal. They cannot be relabeled as application event-to-frame or main-thread timings, and alone do not demonstrate a stable main-thread regression. This limitation also means the calculation-only improvements cannot be used to claim faster native SFTP interaction.

A separate 120-second process sample at 10 ms intervals, `/tmp/serverdash-performance-optimized-interaction.sample.txt`, covered actual interaction epochs **1790500120584–1790500151755** (17:08:40.584–17:09:11.755 +0800) within the sampling window beginning 17:07:42.263. Of 10,747 main-thread samples, the largest branch was event-loop waiting (8,430); accessibility hierarchy calls dominate the main active branch. The prior recursive `setRowHeight`/frame-size loop was **not observed during this sampled interaction**. This is sampling evidence, not a complete long-task trace or proof about every window/operation.

The baseline active-process sample `/tmp/serverdash-performance-baseline-active.sample.txt` reported a **184.4 MiB** peak physical footprint; the optimized interaction sample reported **194.3 MiB** (**5.4% higher**), with current footprint 174.5 MiB. These AppKit QA-process samples have a different scope from the cumulative XCTest resident-memory peaks above. No memory reduction is claimed. Window checks and remaining manual-only coverage are described separately below.
